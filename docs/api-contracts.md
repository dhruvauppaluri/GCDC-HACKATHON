# Draft integration contracts

These JSON shapes are provisional and require workstream owner review before integration.

Candidate profile (website proposal): `{ "candidate_id": "string", "first_name": "string", "last_name": "string", "target_tracks": ["hardware|software|product"], "interests": "string", "resume_text": "string", "skills": {"hardware|software|product": {"skill name": 1}}, "projects": [{"source": "github|website|resume", "url": "string", "summary": "string", "contribution": "string", "selected": true}], "links": {"linkedin_url": "string", "github_url": "string", "website_url": "string"} }`. Ratings range 1–5 and are candidate reported. Only selected projects feed downstream context. Contributions and resume projects entered by the candidate are claims. The UI labels hardware/software/product as HW/CS/PM. Business is outside project scope.

Website API: `POST /api/auth/signup|login`, `POST /api/auth/logout`, `GET /api/me`, `PATCH /api/onboarding/name|interests|skills`, `POST /api/onboarding/resume|complete`, `GET /api/onboarding/options|suggest`, `PATCH /api/profile/links|projects`, `POST /api/profile/import|resume-project`, `GET /api/profile/export`, and `GET /api/jobs/matches`. Session cookie is HTTP-only. The authenticated export returns full resume text and only selected project context with canonical track values. Research jobs can be provided as a JSON array through `RESEARCH_JOBS_FILE`; curated jobs remain available locally.

Research output: `{ "job_id": "string", "track": "hardware|software|product", "title": "string", "company": "string", "required_skills": [], "preferred_skills": [], "eligibility_requirements": [], "source_url": "string", "retrieved_at": "ISO-8601 UTC" }`.

Depth API: `POST /depth/evaluations` accepts multipart form fields `project_id`, `career_track` (`hardware|software|product`), optional `repository_url`, `website_url`, `project_text`, `mode` (`mock|live|codex`) and repeated `files`. It returns `202 {evaluation_id, status}`. `GET /depth/evaluations/{id}` returns status and result/error. `POST /depth/evaluations/{id}/answers` accepts `{ "answers": [{"question_id":"string", "answer":"string"}] }`, returns `202`, and creates a new revision. Poll GET for completion.

Depth result: `{ "project_id": "string", "repository_url": "string|null", "website_url": "string|null", "commit_sha": "string|null", "rubric_version": "track-v1", "criteria": {}, "project_summary": "string", "summary_evidence_ids": [], "architecture_summary": "string", "architecture_evidence_ids": [], "depth_score": "number|null", "confidence": "low|medium|high|unassessed", "dimensions": {}, "demonstrated_skills": [], "unverified_skills": [], "evidence": [], "limitations": [], "follow_up_questions": [], "evaluation_mode": "mock|live|codex", "revision": 0 }`. Dimensions are track-specific as defined in `docs/project-depth-rubric.md`. Each non-null rating is `{ "score": 0-4, "evidence_ids": [] }`; each evidence item contains `id`, `source_type` (`repository|website|document|claim|answer`), `location`, and `excerpt`. Claims and website descriptions cannot alone establish implementation, verification, or demonstrated skills. Revisions preserve prior scores in `history`.

Website case handoff: `POST /api/cases` accepts `{ "job_id": "string" }` for an authenticated, completed candidate with one to five selected projects. It snapshots the candidate and job, starts one Depth evaluation per project, and returns `202 {case_id, status}`. `GET /api/cases/{id}` returns an authenticated versioned bundle with `candidate`, `job`, `project_assessments`, globally namespaced `citations`, `preparation`, and `status` (`pending|partial|complete`). A failed Depth start leaves the project URL in the partial case. `DEPTH_API_URL` points to the local Depth service; `DEPTH_INTEGRATION_MODE` selects `mock|live|codex`. This is the proposed shared input for both lawyers; the current HTTP route requires the candidate session, so a separate Lawyer service needs an authenticated handoff design. Resume text and manually entered resume projects are candidate claims; automatic extraction through Paralegal remains a peer-owned integration task.

Lawyer proposal: two independent arguments consume the same case bundle, identify cited strengths or gaps, and may abstain when evidence is insufficient. A citation refers to a namespaced entry in `citations`; neither lawyer receives simulated outcome labels at inference.

Judge output: `{ "job_id": "string", "candidate_id": "string", "fit_score": null, "confidence": "unassessed", "eligibility": "unknown", "pro_arguments": [], "anti_arguments": [], "skill_gaps": [], "recommendations": [], "verdict": "pending" }`. Eligibility is separate from weighted fit; fit is not a hiring probability. Lawyer and Judge implementations are jointly owned by Rishi and Harsh and are not present in this branch.
